# CLIP-ReID ViT-B/16 — вариант 2: Optuna HPO

Отдельный development-эксперимент, подготовлен 19 сентября 2026 года.
Полный поиск запускает пользователь в [train_clip_hpo.ipynb](train_clip_hpo.ipynb).
Результаты нового обучения ещё не получены. Код: `training/clip_hpo.py`.

## Запуск

1. Открыть notebook с kernel из репозиторного `.venv`.
2. Выполнить **Restart Kernel → Run All**. По умолчанию включены smoke и полный HPO.
3. Держать Mac на питании, с открытой крышкой и без автоматического сна.

Из корня репозитория можно запустить Jupyter так:

```bash
caffeinate -i .venv/bin/python -m jupyter lab
```

Дополнительные пакеты не требуются: используются существующие `requirements-train.txt`.
Ориентир по предыдущему реальному запуску на MPS: около **22 часов поиска** без
досрочного отсева, плюс около **9 часов** двух дополнительных seed. Это оценка,
не обещание времени; нагрузка, checkpoint I/O и скорость диска влияют на итог.

Нужно примерно **27–30 GiB свободного места** для стандартного плана. Проверка
перед началом резервирует расчётный бюджет; перед каждой image-эпохой требуется
ещё 3 GiB свободного места для безопасной атомарной перезаписи. Если место
закончится, эксперимент остановится с объяснением и продолжится после освобождения
места. Автоматического удаления старых весов/результатов нет.

## Протокол

- Те же identity- и exact-frame-disjoint inner train/validation, что в варианте1.
- На текущих данных: 741 train ID, 184 validation ID; 4605 обучающих кропов.
- Только organiser `train.csv`; test query/gallery не используются.
- HPO/seed selection — официальный **raw inner mAP@10**, без реранкинга.
- Чистый inner-trained OSNet77,87% и CLIP variant1 71,82% загружаются из
  проверенных отчётов того же протокола. Это не outer-метрики рабочего MVP.
- Внешние calibration/validation, отказ и финальное обучение не запускаются.
- Повторные seed используют то же разбиение: это не cross-validation и не
  независимый тест. Каждый checkpoint выбирается по внутренней validation.

## Что ищем

| Параметр | Диапазон |
|---|---|
| Encoder LR | 2e-6…2e-5, log |
| LR множитель новых classifier heads | 1 / 5 / 10 / 20 |
| Weight decay | 1e-6…1e-3, log |
| P×K при batch32 | 8×4 / 16×2 |
| Вес ID loss | 0.25 / 0.5 / 1.0 |

Четыре обязательных стартовых trial: текущий рецепт; только head LR×10;
только P16/K2; только ID weight1.0. Ещё восемь конфигураций предлагает Optuna TPE.
Это ограниченный поиск, не полный Grid Search и не гарантия глобального оптимума.

Фиксированы исходный публичный VeRi checkpoint, 256×256, mean/std0.5, BNNeck,
Adam, аугментации, smoothing0.1, triplet margin0.3, веса triplet1 и image-text1.
Множитель головы действует только на `classifier` / `classifier_proj`.
Загруженные BNNeck-параметры сохраняют encoder LR; bias multiplier2 сохранён.
Суммирование потерь двух голов и трёх triplet-ветвей соответствует варианту1.

## Этапы и ограничение бюджета

1. 12 trials, максимум15 image-эпох каждый.
2. Median pruning — только после12-й эпохи, минимум четырёх полностью завершённых
   trials и трёх доступных результатов для сравнения на том же шаге.
3. Top4 завершённых trials продолжаются до35 image-эпох.
4. Top2 после35 эпох продолжаются до60.
5. Победитель60-эпохового этапа повторяется на seed20260916/20260917, **если**
   его прирост относительно CLIP variant1 не меньше0.005 mAP (0,5 п.п.).

`confirmation_min_gain` в `SearchPlan` — явная настройка бюджета, не порог
статистической значимости. Чтобы проверить seed независимо от прироста, можно
заранее поставить0; тогда всё равно требуется не проиграть варианту1.
Менять её после начала нужно в новой папке эксперимента, как и остальные настройки.
Нет автоматического дополнительного HPO, если модель не обгонит OSNet.

У всех image-запусков единый горизонт60: warmup10, LR×0.1 на эпохах30/50.
Продолжение15→35→60 не меняет прошлую траекторию LR, не сбрасывает optimizer и
не начинает новый короткий cosine schedule. При первичном отборе сравниваются
конфигурации с одинаковым бюджетом, а не ранняя эпоха с финальной OSNet-метрикой.

## Промпты и независимость trials

Stage1 фиксирована:60 эпох, Adam, LR3.5e-4, weight decay1e-4, batch64.
Для основного seed проверяется совместимость `variant_01/.../prompt_last.pt`
с текущими кодом, конфигурацией и протоколом, затем создаётся локальная копия.
Замороженные текстовые признаки кэшируются и привязаны к checksum checkpoint.
Новые seed обучают собственные промпты с нуля; HPO weight decay не применяется
к этой общей стадии. Исходные файлы варианта1 никогда не перезаписываются.

Каждый image-trial заново загружает исходный **VeRi checkpoint**, создаёт новые
головы под train ID и получает одинаковый основной seed. Он не начинается с
лучшей image-эпохи53 первого эксперимента или с весов предыдущего trial.
При продолжении того же trial загружается его `image_last.pt`.

## Сохранение и восстановление

- `results/manifest.json`: данные/протокол, код, версии библиотек, план и пространство поиска.
- `results/optuna.sqlite3`: параметры, промежуточные оценки и состояние Optuna.
- `results/progress.json`: активный trial, эпоха, оставшиеся эпохи, время эпохи и ETA.
- `results/runs/<trial>/image_history.json`: потери, три train accuracy, LR, метрики и время.
- `weights/<trial>/image_last.pt`: атомарный источник истины — текущая модель,
  optimizer, история, лучший checkpoint и перечень увиденных изображений.
- `weights/<trial>/image_best.pt`: лучший по raw mAP@10; исходная эпоха0 также кандидат.
  Этот отдельный файл обновляется при завершении/отсеве этапа. Во время обучения
  актуальные лучшие веса после каждой эпохи уже находятся внутри `image_last.pt`.
- У продвинутых trial: `best_after_015.pt` / `best_after_035.pt` для прежних этапов.
- `results/rungs/`: неизменяемые результаты этапов, чтобы повторный Run All не
  пересчитывал top4 по уже доученным до60 эпох моделям.
- `results/experiment_summary.json` и `RESULTS.md`: итог, все seed, среднее/std.

После прерывания **не удалять JSON или SQLite**: Restart Kernel → Run All с теми
же настройками. Незаконченная эпоха повторится с последнего полного checkpoint;
RUNNING-trial возобновится с тем же номером. Завершённый эксперимент не запускается
заново. Изменение данных, кода, пакетов или настроек требует новой папки.
Файловая блокировка не позволяет двум kernel одновременно писать один эксперимент;
она автоматически снимается при завершении процесса.

В Optuna4.x восстановление RUNNING-trial использует storage ID `FrozenTrial._trial_id`;
доступ изолирован в `next_trial` и проверяется тестом на установленной Optuna4.9.0.
Веса, SQLite, feature caches и lock исключены из Git. JSON-отчёты не исключаются.

## Диагностика и параллельная разметка

Кроме mAP/Rank сохраняются accuracy двух ID-heads и image-to-text классификации.
Это помогает проверить гипотезу медленной адаптации головы, но не заменяет ReID-метрики.

Размечайте подготовленный HTML из `OSNet-AIN-x1.0/audit_07_errors_masks/results/`.
Исходные изображения/CSV не редактировать: маски сохраняются отдельным JSON.
HTML-разметка не занимает MPS. Второе обучение или запуск GPU-аудита параллельно
конкурируют за память/время — парный аудит лучше запустить после HPO.
Ни этот notebook, ни новый модуль не изменяют MVP, индекс галереи или готовые маски.

## Исследованные источники и принятые решения

- [CLIP-ReID: официальный VeRi config](https://github.com/Syliz517/CLIP-ReID/blob/master/configs/veri/vit_prom.yml):
  подтверждены LR5e-6, warmup10, epochs60, веса loss0.25/1/1, BNNeck/inference.
  Маленький LR не объявляется ошибкой — это исходная авторская настройка.
- [CLIP-ReID optimizer](https://github.com/Syliz517/CLIP-ReID/blob/master/solver/make_optimizer_prompt.py):
  повышение LR новых heads — проверяемая локальная гипотеза, не обещанный прирост.
- [PCL-CLIP](https://github.com/RikoLi/PCL-CLIP): прямое fine-tuning image encoder
  с прототипами без prompts. Отложено: это отдельная loss/memory реализация, не SupCon.
- [CLIP-LoRA](https://github.com/MaxZanella/CLIP-LoRA): адаптеры для few-shot
  классификации. Отложено: результаты не доказывают улучшение нашего vehicle ReID.
- [Optuna MedianPruner](https://optuna.readthedocs.io/en/stable/reference/generated/optuna.pruners.MedianPruner.html):
  отсрочка pruning и сравнение по промежуточным оценкам на одном шаге.

Никаких новых внешних датасетов, LoRA/PCL или camera/view metadata на вход модели
не добавлено. Источник весов и ограничения лицензий — [SOURCES.md](../SOURCES.md).
