# Оптимизация без замены MVP_fusion_v25 — 2026-09-29

Эталон: `91d559c2e0024fd117f74943781b6b9ee84c997d`. Изменения находятся в
продуктовом коде, не в обучении. Это локальная CPU-проверка, не официальный
benchmark NVIDIA/A5000 и не повторная оценка mAP на закрытом тесте.

## Результат

Ускорение есть, но небольшое на уровне всего CPU-пайплайна. Основную стоимость
по-прежнему составляют четыре forward модели. Все три конкурсных файла
до/после **побайтово идентичны**. Машиночитаемые замеры, hashes реализации и
выходов: [CPU_OPTIMIZATION_2026-09-29.json](CPU_OPTIMIZATION_2026-09-29.json).

| Измерение | До | После | Сокращение времени |
|---|---:|---:|---:|
| Полный экспорт 1860 изображений, по одному новому запуску | 185,168 с | 180,489 с | 2,53% |
| Extract 64 изображений, медиана 6 чередующихся повторов | 6,188 с | 6,102 с | 1,39% |
| Только preprocessing 64 изображений, медиана 10 повторов | 217,126 мс | 177,163 мс | 18,41% |

Во всех шести парных замерах extract обновлённая версия была быстрее, но
разбросы отдельных времён пересекаются: это умеренный локальный эффект,
не обещание такого же процента на другом устройстве. 18,41% относится только
к preprocessing, не к полному inference. Для заметно большего общего ускорения
понадобится работа с вычислением самих сетей и отдельная проверка на GPU.

Сохранены точные входные float32-массивы 208/256 для всех 1860 изображений,
все `(1860, 2048)` выходные embeddings, 1110 top-10, 1069 кандидатов с confidence
и 41 отказ. Это доказательство отсутствия изменения решений на данном наборе,
а не оценка их правильности по неизвестным тестовым меткам. Историческая
development-validation mAP@10 0,8289573904 не пересчитывалась и не повышалась.

на хосте не установлен `psycopg`; попытка host-миграции остановилась до обращения

выполнены внутри контейнера с текущим кодом, смонтированным read-only. Рабочая
БД и демо на 8017 не затрагивались. Предупреждения о deprecated TestClient/anyio
не скрывались и не потребовали изменения runtime-зависимостей.

Offline smoke использовал существующий CPU-образ `vehicle-reid:fusion-v25`
с текущими исходниками и весами, подключёнными read-only, без train.csv, БД и сети.
Это подтверждает автономность обновлённого кода, но не является чистой пересборкой
нового CPU/GPU Docker-образа. Поставочный Dockerfile по-прежнему фиксирует Node
24.15.0; локальная сборка UI выполнялась установленным Node 22.19.0.

Новые сырые экспорты, JSON, XML тестов и тестовый gallery-кэш находятся в
игнорируемом `artifacts/cpu-optimization-20260929/`. Изображения, embeddings и
исследовательские результаты в поставку не добавляются.

Новая Linux amd64/CUDA-сборка, её скорость, полная GPU-повторяемость и
CPU/CUDA parity **не проверены**: на этом Mac нет NVIDIA. Исправление NVRTC
основано на уже полученном внешнем успешном запуске исходного кода. Мак-проверки
не закрывают `official_submission_ready=false` и не предсказывают баллы A5000.

## Что изменено

1. EXIF → RGB → проверка BBox → crop выполняются один раз для двух ветвей.
   Из общего crop независимо получаются прежние входы 208×208 и 256×256.
   Интерполяция, значения ImageNet, порядок float32-операций не менялись.
2. CPU-массив R1-батча создаётся один раз и передаётся всем трём энкодерам.
   Каждый сохраняет проверки формы/конечности; `session.run` остаётся синхронным.
   Это не CUDA I/O binding и не изменение размещения выходных векторов.
3. Один экспорт использует один индекс путей изображений для query и gallery.
   Проверки отсутствующих/неоднозначных ID, хэши байтов и CSV до/после вычисления,
   а также атомарная публикация готового кэша сохранены.
4. В GPU-зависимости добавлен `nvidia-cuda-nvrtc-cu12==12.2.140`, а путь библиотеки —
   в Dockerfile. Это перенос двух исправлений из полученного отчёта RTX 4060 Ti,
   а не измеренное GPU-ускорение.

Не менялись: все веса и frozen JSON, порог `0.534365177154541`, смесь ranking
50/50, k-reciprocal, кандидат R1 raw-top1, FP32, отключённый TF32, cuDNN DEFAULT,
параметры workspace, batch по умолчанию 16 и официальный evaluator.
Fingerprint реализации меняется намеренно: после обновления gallery-кэш
строится заново; старый кэш не подменяется и остаётся пригодным для отката к старому коду.

## Методика локального сравнения

Mac Apple M4 Pro, 24 GiB RAM, macOS ARM64. ONNX Runtime CPU 1.30.0;
один и тот же Python и набор библиотек для обеих версий, intra-op=2/inter-op=1.
`OPENBLAS_NUM_THREADS=1`, `OMP_NUM_THREADS=1` одинаковы для обеих версий;
настройки поставочного приложения этими переменными не изменялись.

- Два новых полных экспорта в отдельных процессах: 1110 query + 750 gallery.
  Gallery строится с нуля; все хэши, поиск, реранкер, файлы и валидация включены.
- Требуется побайтовое совпадение всех трёх конкурсных файлов, а не только
  близость эмбеддингов. Никакие допуски ради прохождения не добавляются.
- На всех 1860 изображениях отдельно сравниваются оба входных массива float32.
- Для повторных замеров берутся 64 равномерно распределённых по порядку CSV
  изображения; batch=16, по 16 прогревочных изображений для каждой версии,
  шесть повторов с чередованием порядка A/B и B/A. Измеряются индексирование,
  чтение, decode, preprocessing, четыре forward и нормализация, без поиска.
- Preprocessing отдельно: те же 64 предварительно декодированных изображения,
  десять чередующихся повторов. Это время только одного этапа, не всей системы.

Числа полного запуска — одиночные наблюдения, зависящие от файлового кэша,
фоновой нагрузки и температуры. Повторные замеры надёжнее, но также относятся
только к этому Mac и данному набору. Тяжёлые тесты и сборка UI во время измерений
не запускались; существующее демо не перезапускалось.

## Как повторить

Из корня актуального проекта с активированным Python 3.11 окружением и
CPU-зависимостями. В командах предполагается `dataset/`; при необходимости
укажите свой абсолютный путь. Используйте новый каталог результатов.

```bash
REID_PROJECT="$PWD"
REID_PYTHON="$(command -v python)"
REID_DATASET="$REID_PROJECT/dataset"
REID_OUTPUT="$REID_PROJECT/artifacts/cpu-optimization-repeat"
REID_BASELINE="$(mktemp -d)"
git archive 91d559c2e0024fd117f74943781b6b9ee84c997d backend models evaluate.py \
  | tar -xf - -C "$REID_BASELINE"
export OPENBLAS_NUM_THREADS=1 OMP_NUM_THREADS=1

(cd "$REID_BASELINE" && "$REID_PYTHON" -m backend.infer \
  --dataset "$REID_DATASET" --output "$REID_OUTPUT/before" \
  --profile MVP_fusion_v25 --provider CPUExecutionProvider)
"$REID_PYTHON" -m backend.infer \
  --dataset "$REID_DATASET" --output "$REID_OUTPUT/after" \
  --profile MVP_fusion_v25 --provider CPUExecutionProvider
"$REID_PYTHON" -m tools.verify_cpu_optimization \
  --baseline "$REID_BASELINE" --dataset "$REID_DATASET" \
  --before-export "$REID_OUTPUT/before" --after-export "$REID_OUTPUT/after" \
  --output "$REID_OUTPUT/comparison.json"
```

Инструмент явно проверяет совпадение источников полного экспорта и повторных
замеров. `backend.compare_exports` для повторов одной версии не ослаблен:
его строгая проверка fingerprint остаётся прежней. Здесь разные fingerprint
ожидаемы, но веса, preprocessing, политики, входы и все три файла должны совпасть.

Официальный runner `backend.benchmark` не менялся: 50 прогревов, 300 batch=1
замеров, batches 1/8/16/32 минимум по 10 секунд, затем полный extract и память.
Этот сравнительный CPU-скрипт его не заменяет.
