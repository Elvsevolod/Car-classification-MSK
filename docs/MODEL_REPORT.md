# Активная модель: протокол, калибровка и ограничения

Этот отчёт описывает сохранённую **локальную development-оценку**, а не результат скрытого теста организаторов. Числа перенесены из ранее полученного `artifacts/baseline_metrics.json`; машинно-читаемый отчёт и порог поставляются в [`models/calibration.json`](../models/calibration.json). Изменения Docker, API и интерфейса не являются новым обучением или новым измерением качества.

## Модель и поиск

- Активные веса: [`osnet_ain_x1_0_vehicle_reid_hpo_best_map.onnx`](../models/osnet_ain_x1_0_vehicle_reid_hpo_best_map.onnx), OSNet-AIN x1.0, HPO best-mAP checkpoint эпохи 5.
- Development-обучение: 925 identity, BNNeck и supervised contrastive loss. Конфигурация и checkpoint выбирались по локальной validation, поэтому она **не является независимым финальным тестом**.
- Размер ONNX: 8 754 346 байт. SHA-256: `01466f503232467224774b6e3bafe6c4393b1de30b47b1bd714908a62f2006a2`.
- Preprocessing: EXIF-ориентация → RGB → строгий BBox без отступов → bilinear 208×208 → float32 / 255 → ImageNet normalization → NCHW → ONNX → L2-нормированный 512-D вектор.
- Версия preprocessing: `exif-rgb-bbox-bilinear208-imagenet-l2-v1`; fingerprint encoder: `b2023e8adebccdcc12f26ab729adaeced1ac4cb0fd8c0712ceb04fb9b06293ef`.
- Порядок результатов: streaming k-reciprocal reranking, `k1=20`, `k2=3`, `lambda=0.5`. Граф строится только по статичной gallery; каждый query обрабатывается независимо.
- Решение об отказе: максимум **raw cosine по всей gallery**, а не rerank score. Номерные знаки, OCR, детектор и другие query не используются.

Сведения о происхождении исходных весов, лицензии и проверке ONNX приведены в [`models/README.md`](../models/README.md). В этом этапе исправлений веса, preprocessing, формулы evaluator и алгоритм reranking не заменяются.

## Локальный протокол

Разметки `vehicle_id` для официальных `test_query.csv` / `test_gallery.csv` нет, поэтому их mAP по имеющимся файлам вычислить нельзя. Локальная оценка использует размеченный `train.csv` и код [`backend/evaluate.py`](../backend/evaluate.py).

1. Seed — `20260915`. Разделение выполняется примерно 60/20/20 по группам identity: **925 train / 307 calibration / 309 validation**. Calibration и validation identity не участвуют в development-обучении.
2. Identity, связанные одинаковыми SHA-256 исходных кадров, объединяются в одну группу и не расходятся по разделам. Это защита от точных копий, а не от похожих соседних кадров.
3. Для каждой calibration/validation identity выбирается один query; gallery содержит объекты этой identity с других камер. Для примерно 20% identity их gallery-объекты полностью убираются, имитируя отсутствие совпадения.
4. `camera_id` нужен только для формирования и оценки этого протокола; он не подаётся модели и не требуется в пользовательском поиске.
5. Порог выбирается **только на calibration**, затем фиксируется для validation и batch-export. Validation уже использовалась для выбора HPO/checkpoint: identity-disjoint разбиение не отменяет эту зависимость.

При повторной оценке `splits.json` сохраняет identity, query/gallery ID, seed, hash `train.csv` и SHA-256 кадров. Финальное переобучение на train+validation потребовало бы новой независимой проверки; приведённые ниже результаты нельзя переносить на такую модель.

## Метрики и официальный evaluator

Формулы берутся из неизменённого [`evaluate.py`](../evaluate.py), SHA-256: `655c71db8c2e4d2cd7680c40c768afacfdffff360401111c1a46df921551ffa3`. Адаптер [`backend/scoring.py`](../backend/scoring.py) формирует предсказания и вызывает его функции.

- mAP@10 и Rank-1/5 учитывают query с хотя бы одним допустимым позитивом. AP@10 нормируется на `min(n_pos, 10)`.
- Junk — совпадение **одновременно** `vehicle_id` и `camera_id`. Негативы той же камеры не исключаются.
- Внутри официального evaluator junk удаляется **до** ограничения `[:top_k]`. Однако локальный адаптер и `submission.csv` уже содержат только первые 10 объектов (или всю gallery, если она меньше). Поэтому после удаления junk нельзя дополнить список объектом с исходного 11-го места. Это важное различие между оценкой усечённого файла и полного ранжирования; текущий экспорт не меняет контракт ради скрытого восполнения списка.
- Full mAP и mINP — справочные метрики полного cosine-ранжирования исходных embeddings, **не** reranking.
- Candidate Precision/Recall/F1 считаются официальной функцией на уровне query по верхнему кандидату. В частности, неверный принятый кандидат учитывается как FP, а отказ при наличии позитива — как FN; не следует подменять эти числа своей pair-level формулой.
- TNR — доля корректных отказов среди query без допустимого позитива. PR-AUC также берётся из официальной функции, где отказам соответствует отсутствующий confidence (`-inf`).

## Порог и семантика confidence

Зафиксированный порог raw cosine: **`0.5948754549026489`**. Критерий калибровки — максимум `0.7 * candidate_F1 + 0.3 * TNR` на calibration. При равенстве этого значения выбирается больший F1, затем больший порог, как в `backend.scoring.calibrate`.

Query принимается, если `max(raw_cosine) >= threshold`; иначе возвращается отказ. После принятия порядок кандидатов задаёт reranking. Этот порог не означает, что каждый показанный объект сам преодолел его или что личность автомобиля подтверждена.

В API `confidence` — максимальный raw cosine в диапазоне [−1, 1]. В `candidates.csv` пишется один верхний reranked-кандидат на принятый query, а его `confidence = (max_raw_cosine + 1) / 2` лежит в [0, 1]. Соответствующий порог этой шкалы — примерно `0.7974377274513245`. **Обе шкалы — similarity score, не вероятность.** При отказе строк этого query в `candidates.csv` нет, но его Top-10 остаётся в `submission.csv`.

API и автономный batch-export читают один bundled `models/calibration.json` и проверяют совместимость с моделью, encoder fingerprint, preprocessing и параметрами reranking. Пустой runtime-volume не требует новой калибровки. Несовместимый или повреждённый manifest должен давать явную ошибку, а не подставлять произвольный порог. Ручной порог в API остаётся пользовательским override и отмечается `threshold_source=manual`; по умолчанию источник — `calibration`.

## Сохранённые результаты

| Метрика | Calibration | Validation |
|---|---:|---:|
| mAP@10, streaming reranking | 78,72% | 81,47% |
| Rank-1 | 79,27% | 80,16% |
| Rank-5 | 87,80% | 88,26% |
| Candidate Precision | 78,95% | 79,68% |
| Candidate Recall | 67,26% | 67,12% |
| Candidate F1 | 72,64% | 72,86% |
| TNR | 72,13% | 79,03% |
| PR-AUC | 89,66% | 89,79% |
| `0.7 * F1 + 0.3 * TNR` | 72,49% | 74,71% |
| Full mAP исходных embeddings | 77,29% | 80,36% |
| mINP исходных embeddings | 69,44% | 74,07% |
| Query с совпадением / без совпадения | 246 / 61 | 247 / 62 |
| TP / FP / FN / TN | 150 / 40 / 73 / 44 | 149 / 38 / 73 / 49 |

Справочный raw-cosine baseline того же checkpoint и тех же разделов, без reranking, имеет mAP@10 **75,60% / 79,02%** (calibration / validation). Это сравнение порядка выдачи при одной модели, а не доказательство устойчивого выигрыша на других разбиениях. При фиксированном пороге raw confidence и TNR не меняются; F1 может измениться из-за смены верхнего кандидата.

## Производительность и ограничения

Сохранённый CPU-замер: macOS 15.7.3 ARM64, ONNX Runtime, 2 intra-op потока, batch=1; 3 прогрева и 30 измерений одного изображения. JPEG decode + preprocessing + inference + L2: медиана **15,35 мс**, p95 **16,44 мс**. Время поиска по БД, reranking, HTTP и отрисовки UI сюда не входит. Это **не** benchmark RTX A5000, end-to-end latency сервиса или throughput.

- Runtime пока использует `CPUExecutionProvider`; GPU-профиль и конкурсный GPU benchmark не подтверждены.
- Текущие числа — локальный holdout с синтетическими no-match query. Изменение состава gallery и реальная доля неизвестных автомобилей могут ухудшить качество отказа.
- Validation участвовала в выборе checkpoint, поэтому результат нельзя объявлять независимой оценкой обобщения.
- PostgreSQL demo выполняет точный поиск; граф reranking имеет квадратичные по gallery структуры. Масштабирование на большие gallery отдельно не доказано.
- Тесты API/Docker/форматов проверяют программный контракт, но не заменяют ML-оценку. См. [`TEST_SUMMARY.md`](TEST_SUMMARY.md) как отдельный инженерный отчёт.
- Проверка поставки на чистом целевом Linux `amd64` и полная готовность к конкурсу — отдельный этап, не следствие изменения UI.

## Повторная локальная оценка

Для разработки, при наличии размеченного `train.csv` и установленных Python-зависимостей:

```bash
python -m backend.evaluate --output artifacts/local-evaluation
```

Команда пересоздаёт локальный split/report и заново калибрует порог в указанной папке. Это отдельная исследовательская операция, **не** путь конкурсного inference и не автоматическая замена bundled manifest. Перед заменой активных весов/порога нужно проверить качество, совместимость и воспроизводимость; старые результаты сохраняются отдельно.

Для данных без `train.csv` используется только `python -m backend.infer --dataset /data --output /out`; он не оценивает качество скрытого теста и не подбирает по нему порог. Команды Docker и форматы файлов приведены в [README](../README.md).
