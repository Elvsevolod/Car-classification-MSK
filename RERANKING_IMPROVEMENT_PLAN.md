# План улучшения реранкинга Vehicle ReID

Дата: 21 сентября 2026 года. Статус: план экспериментов; действующий MVP и его веса не меняются.

## Цель и трактовка идеи

Повысить официальный mAP@10 по финальному `submission.csv` и качество отказа по
`candidates.csv`, сохранив независимую обработку каждого запроса. Под
«реранкером с инструкцией» здесь понимается мультимодальная модель, которая
получает два кропа и текстовое правило сопоставления *конкретного* автомобиля.
Под «дообучением реранкера» — обучение отдельной модели оценки пары: текущий
k-reciprocal алгоритм не содержит обучаемых весов.

Источник требований — [ТЗ](../7.%20Фалькон%20Тех.pdf) и более поздние
[ответы организаторов](ORGANIZER_QA.md). Источник формул — неизменённый
[официальный evaluator](evaluate.py).

## Ограничения эксперимента

- Финальный mAP@10 считается по десяти ID в `submission.csv`. Оценка
  `embeddings.npy` даёт справочные метрики, поэтому порядок после реранкинга
  может отличаться от порядка по cosine.
- Разрешены статичная галерея и **один текущий query**. Парная модель поверх
  первичного top-K допустима; другие query, их результаты и подстройка по
  закрытому тесту недопустимы.
- Отказ кодируется только отсутствием строк query в `candidates.csv`.
  `submission.csv` всё равно содержит десять кандидатов.
- Суммарный размер всех файлов весов, участвующих в инференсе, — не более
  2 ГБ. Запуск должен работать без сети. Реранкинг не входит в официальный
  замер времени `extract()`, но его время нужно измерить для потокового сценария.
- На вход решения не передаются `camera_id`, время и география. Нельзя
  использовать номер, остаточные признаки его размытия, OCR или фон как
  основание для установления идентичности. `camera_id` допустим только для
  формирования обучающих пар и локального протокола оценки.

## Зафиксированная исходная точка

Активный пайплайн: OSNet-AIN x1.0, HPO best-mAP epoch 5, потоковый
k-reciprocal реранкинг `k1=20`, `k2=3`, `lambda=0.5`; отказ по максимальному
исходному cosine с порогом `0.5948754549026489`. Реализация —
[`backend/rerank.py`](backend/rerank.py), отчёт —
[`artifacts/baseline_metrics.json`](artifacts/baseline_metrics.json).

| Локальная validation | Без реранкинга | Действующий реранкинг |
|---|---:|---:|
| mAP@10 | 0,7902 | **0,8147** |
| Rank-1 | 0,7895 | **0,8016** |
| Rank-5 | **0,9028** | 0,8826 |
| Candidate F1 | 0,7255 | **0,7286** |
| TNR | 0,7903 | 0,7903 |

На validation 247 query имеют допустимое совпадение, 62 — не имеют. Разбиение
содержит 925 identity для обучения, 307 для calibration и 309 для validation;
в обучающей части 5717 изображений. Исходные идентичности разделены, а
одинаковые по SHA-256 полные кадры сгруппированы при построении сплита.

Диагностика по сохранённым OSNet-эмбеддингам и
[`artifacts/splits.json`](artifacts/splits.json): хотя бы один допустимый
позитив находится в исходном top-10 у 234/247 query, в top-50 — у 242/247.
Идеальная перестановка кандидатов из исходного top-50 дала бы верхнюю границу
mAP@10 около `0,9636`. Это математический потолок данного списка, а не
ожидаемый результат обучаемой модели. Пять query без позитива в top-50 таким
реранкером не исправить.

В [аудите режима кандидатов](OSNet-AIN-x1.0/audit_07_errors_masks/results/errors.json)
111 ошибочных решений: 73 ошибочных отказа при существующей паре, 25 принятых
совпадений с другой машиной и 13 принятых query без пары. В 49 из 73
ошибочных отказов правильная машина уже стоит первой. Поэтому порядок
кандидатов и решение «ответить или отказаться» оцениваются отдельно.

## Очерёдность экспериментов

### 1. Дешёвый контроль без новой большой модели

На неизменных эмбеддингах сравнить действующий k-reciprocal с небольшими
изменениями его оценки: фиксированным смешиванием cosine и графовой оценки,
сигналом взаимных соседей и поддержкой кандидата ближайшими изображениями
галереи. Оценивать только top-50 одного query; граф галереи можно вычислить
заранее. Все коэффициенты выбирать на calibration, затем фиксировать.

Этот контроль нужен, чтобы обучаемая модель доказывала прирост относительно
лучшего недорогого решения, а не только относительно исходного cosine.

### 2. Компактный обучаемый парный реранкер — основной кандидат

Для каждого обучающего query собрать top-50 тем же первым этапом поиска, что
будет использоваться на инференсе. Позитивы — кадры того же ТС с других камер;
негативы — прежде всего похожие машины, высоко поднятые OSNet. Случайные
негативы можно оставить как малую контрольную долю: на них задача слишком
проста. Не считать пары одного identity независимыми примерами.

Начать с небольшого классификатора или ранжирующей головы над уже доступными
признаками: cosine, k-reciprocal score, положение в исходном списке,
`|e_q-e_g|`, `e_q*e_g`, разрыв до соседних оценок. По необходимости добавить
локальные визуальные признаки автомобиля, но сначала измерить вклад простой
модели. Выход — числовая оценка пары; её можно смешивать с исходной оценкой,
не меняя OSNet-эмбеддинги и справочные метрики `embeddings.npy`.

Для честного внутреннего отбора разделить 925 development identity на
identity- и frame-disjoint части. Активная OSNet уже обучалась на всех этих
identity, поэтому её эмбеддинги сами по себе не дают полностью независимую
inner validation. Для окончательного сравнения голов использовать
out-of-fold признаки либо отдельный OSNet-контроль, обученный без inner-val
identity. Внешние calibration и validation не использовать для обучения
головы или выбора её эпохи.

Если признаки готовых эмбеддингов не помогают, следующий вариант — компактный
визуальный модуль сопоставления локальных карт двух кропов. Это отдельный
эксперимент с замером размера и времени, а не обязательный этап.

### 3. Инструкционный мультимодальный реранкер — ограниченный пилот

[Qwen3-VL-Reranker-2B](https://huggingface.co/Qwen/Qwen3-VL-Reranker-2B)
умеет оценивать пару изображений с настраиваемой текстовой инструкцией.
Исходный BF16-файл весов занимает 4,26 ГБ и **не проходит** лимит кейса.
Квантованную сборку можно рассматривать только после проверки полного
размера всех весов, воспроизводимости офлайн-запуска, времени top-K и потери
качества от квантования. Зафиксировать URL, автора, commit/версию, лицензию и
checksum каждого внешнего артефакта.

Пилот: два одинаковых набора сложных пар из train/inner validation, одна
заранее записанная инструкция на английском, сравнение с компактной моделью.
Инструкция должна требовать совпадения именно физического автомобиля по
кузову, фарам, дискам, наклейкам и повреждениям при смене ракурса и освещения;
запрещать опору на номер, людей и фон. Текстовая инструкция сама по себе не
гарантирует, что модель не смотрит на запрещённую область. Это проверить
отдельным парным прогоном с закрытой областью номера. Опубликованные общие
бенчмарки Qwen не являются оценкой качества vehicle ReID.

Не дообучать крупную мультимодальную модель, пока её фиксированная версия
не покажет полезный сигнал на этой задаче и не появится допустимый по размеру
и скорости способ запуска.

## Оценка и правило выбора

1. Новые парные методы получают один и тот же исходный top-50 по OSNet,
   формируют финальный top-10 и проверяются неизменённым `evaluate.py`.
   Действующий реранкер по всей галерее остаётся отдельным неизменённым
   контролем. Учитывать junk только по официальному правилу: совпадают и
   `vehicle_id`, и `camera_id`.
2. Параметры ранжирования и порог отказа выбирать на calibration. Для отказа
   сравнить исходный maximum cosine, максимальную оценку новой пары и признаки
   уверенности в лучшем кандидате. Не подбирать порог на validation.
3. Один раз проверить замороженные варианты на validation. Показать mAP@10,
   Rank-1/5, F1, TNR, `0.7·F1+0.3·TNR`, изменения по отдельным query и парный
   bootstrap-интервал для прироста mAP@10. Отдельно измерить время на query,
   время построения графа, суммарный размер весов и повторяемость результата.
4. Проверить устойчивость к закрытию области номера на имеющихся ручных
   масках. Этот небольшой аудит — диагностический; он не заменяет основную
   validation и не доказывает полной независимости от этой области.

Целевой эффект для продвижения: около **+1 процентного пункта mAP@10** к
`0,8147` при положительном парном сравнении и без существенного ухудшения
F1/TNR. Меньший прирост считать предварительным и разбирать по query.
Обязательные условия — лимит 2 ГБ, офлайн-запуск и независимость от других
query. Ни один эксперимент не заменяет активный MVP автоматически.

## Что должно остаться после эксперимента

- Отдельные конфигурация, веса, отчёт, список обучающих identity и hashes
  данных/кода; действующие артефакты MVP сохранены.
- Таблица одинаковых для всех вариантов метрик и времени, перечень query с
  улучшением и ухудшением, итог «принять / отклонить / требуется повтор».
- Если вариант принят — обновлённые `submission.csv` и `candidates.csv` из
  одного воспроизводимого пайплайна и проверка полного запуска одной командой.
