# План создания ансамблевой системы

Дата: 21 сентября 2026 года. Статус: план проверки гипотезы. Под двумя
моделями здесь понимаются действующая **OSNet-AIN x1.0** и обученная
**CLIP-ReID ViT-B/16**. Активный MVP и его веса этим планом не заменяются.

## Идея и ожидаемый эффект

Обе модели независимо извлекают признаки одного и того же кропа автомобиля.
Их оценки сходства объединяются, затем потоковый реранкер уточняет порядок
кандидатов. Гипотеза: CLIP может исправить часть ошибок OSNet, даже если его
собственная средняя метрика ниже. Прирост возможен только при достаточно
разных ошибках моделей; само добавление второго encoder его не гарантирует.

Проверять прежде всего **слияние признаков двух моделей с уже существующим
k-reciprocal реранкингом**, без обучения третьей модели. Обучаемый парный
реранкер из [отдельного плана](RERANKING_IMPROVEMENT_PLAN.md) имеет смысл
добавлять лишь после доказанного полезного сигнала от двух encoder.

## Что известно сейчас

| Результат | Значение | Ограничение сравнения |
|---|---:|---|
| Активная OSNet + реранкинг, outer validation mAP@10 | **0,8147** | 247 query с парой; результат уже использовался при обсуждении MVP |
| Чистый OSNet-контроль, raw inner mAP@10 | **0,7787** | Один внутренний протокол с CLIP |
| Лучший checkpoint CLIP-ReID, raw inner mAP@10 | **0,7580** | Без реранкинга и outer validation |
| CLIP-ReID, среднее трёх seed raw inner mAP@10 | **0,7556** | Те же inner identity; seed не заменяют новый split |

Источники: [метрики MVP](artifacts/baseline_metrics.json),
[отчёт CLIP-HPO](CLIP-ReID-ViT-B-16/variant_02_hpo/results/RESULTS.md).
Цифры из разных строк таблицы нельзя напрямую вычитать: outer OSNet и inner
CLIP оценивались на разных identity и с разным реранкингом. CLIP пока не
проверялся на тех же outer calibration/validation, что активный MVP.

По текущим OSNet-эмбеддингам хотя бы один допустимый позитив находится в
исходном top-50 у **242 из 247** известных outer-validation query. Значит,
объединение двух top-50 может повысить охват запросов максимум на пять
случаев по признаку «нашёлся хотя бы один позитив». Влияние на mAP@10 может
быть шире: для него важны число позитивов и их позиции, а также удаление
ложных совпадений. Степень дополнения CLIP пока не измерена.

## Подтверждение в исследованиях

- [Gao et al., CVPR Workshops 2020](https://openaccess.thecvf.com/content_CVPRW_2020/papers/w35/Gao_Vehicle_Re-Identification_Based_on_Complementary_Features_CVPRW_2020_paper.pdf):
  несколько vehicle-ReID сетей, нормализация и объединение признаков,
  последующий реранкинг. В их собственной self-validation абляции без
  реранкинга объединённые признаки дали 74,8% mAP против 72,0% у лучшей
  отдельной модели.
- [Moral et al., CVPR Workshops 2020](https://openaccess.thecvf.com/content_CVPRW_2020/html/w35/Moral_Vehicle_Re-Identification_in_Multi-Camera_Scenarios_Based_on_Ensembling_Deep_Learning_CVPRW_2020_paper.html):
  ансамбль ReID-признаков и реранкинг в одном пайплайне.
- [Luo et al., CVPR Workshops 2021](https://openaccess.thecvf.com/content/CVPR2021W/AICity/papers/Luo_An_Empirical_Study_of_Vehicle_Re-Identification_on_the_AI_City_CVPRW_2021_paper.pdf):
  сравнение отдельных backbone и ансамбля после обработки результатов.

Эти работы подтверждают осмысленность архитектуры, **не прогнозируют прирост
на нашем датасете**. В них встречаются query expansion, псевдоразметка test,
траектории и метаданные камер. В текущем кейсе переносимы только допустимые
части: визуальные признаки, объединение оценок и реранкинг одного query
относительно статичной gallery.

## Контракт организаторов

Главные источники — [ТЗ](../7.%20Фалькон%20Тех.pdf), более поздние
[ответы организаторов](ORGANIZER_QA.md) и неизменённый
[эталонный evaluator](evaluate.py).

- На инференсе доступна вся статичная gallery и **один текущий query**.
  Запрещены сведения о других query, cross-query expansion/кластеризация и
  подбор параметров по ответам закрытого теста.
- Итоговый mAP@10 берётся из `submission.csv`; в нём всегда десять gallery ID
  на query. `embeddings.npy` требуется отдельно для справочных метрик и
  проверки представления. Отказ — отсутствие строк query в `candidates.csv`.
- Изображение кропается по выданному BBox. Номер, остатки его блюра, OCR,
  `camera_id`, время и географию не использовать как признаки инференса.
- Все веса инференса вместе должны занимать не более 2 ГБ; запуск — офлайн.
  В официальный замер `extract()` войдут **оба** encoder, предобработка и
  постобработка. Время поиска и реранкинга измеряется отдельно. Полные баллы
  за скорость: latency batch=1 не выше 40 мс и throughput не ниже 100 FPS на
  стенде RTX A5000; между порогами баллы снижаются.

## Архитектуры для сравнения

### A. Взвешенное объединение признаков — основной вариант

Для каждого изображения получить L2-нормированные векторы `o` от OSNet и `c`
от CLIP. При весе OSNet `a` в диапазоне `[0, 1]` объединённый вектор:

```text
z = concat(sqrt(a) * o, sqrt(1 - a) * c)
cos(z_q, z_g) = a * cos(o_q, o_g) + (1 - a) * cos(c_q, c_g)
```

Векторы разных моделей нельзя складывать покомпонентно: они имеют разные
размерности и обучены в разных пространствах. Конкатенация сохраняет один
фиксированный embedding для `embeddings.npy` и даёт понятную оценку сходства.
На нём строится статичный граф gallery, после чего существующий потоковый
k-reciprocal реранкер обрабатывает каждый query независимо.

На calibration выбрать небольшой заранее заданный набор весов `a`, затем
при необходимости подобрать параметры реранкинга. Ранее выбранные
`k1=20`, `k2=3`, `lambda=0.5` и cosine-порог отказа нельзя автоматически
переносить на новое распределение оценок.

### B. Раздельный поиск и объединение кандидатов — контроль

Получить top-K отдельно по OSNet и CLIP, взять объединение ID без дублей,
затем упорядочить по двум cosine-оценкам и графовому score. Этот вариант
проверяет, добавляет ли CLIP позитивы, которых нет в списке OSNet. При gallery
из 750 изображений сравнить каждый query со всей gallery обеими моделями
несложно, поэтому обрезать списки *до* слияния без причины не нужно.

### C. Обучаемая оценка пары — только следующий этап

Если A или B улучшают качество, но остаются ошибки порядка, использовать
оценки обеих моделей как признаки компактного парного реранкера. Обучать его
только на development train identity с трудными негативами; подбор, отказ и
независимая проверка описаны в
[плане реранкинга](RERANKING_IMPROVEMENT_PLAN.md). До результата вариантов A/B
это дополнительная сложность без проверенной необходимости.

## Порядок проверки

1. **Зафиксировать источники.** Точные checkpoints, SHA-256, код, preprocessing,
   разбиение, версию evaluator и правила маскирования. Экспортировать
   image encoder выбранного CLIP checkpoint для инференса и проверить parity
   с обучающей реализацией. Исходные веса и MVP не перезаписывать.
2. **Сравнить ошибки на одном протоколе.** Посчитать OSNet и CLIP на одних
   calibration query/gallery: raw mAP@10, Rank-1/5, recall допустимых позитивов
   в top-10/top-50, число найденных позитивов и пересечение ошибочных query.
   Отдельно посчитать верхнюю границу от объединения двух candidate pool.
3. **Подобрать простое слияние.** На calibration сравнить OSNet, CLIP,
   ограниченную сетку весов A, вариант B и их потоковый реранкинг. Порог
   отказа подобрать заново только на calibration; он оценивается отдельно от
   порядка кандидатов.
4. **Заморозить один вариант и проверить.** Один раз получить результаты на
   outer validation через `evaluate.py`: mAP@10, Rank-1/5, F1, TNR, ошибочные
   query и парный интервал для изменения mAP. Эта validation уже фигурировала
   в прежних решениях проекта, поэтому не выдавать её за полностью невидимый
   финальный тест и не подбирать вариант повторно по её результату.
5. **Проверить стоимость.** Замерить обе модели в полном `extract()` на
   RTX A5000, throughput, VRAM, суммарный размер всех участвующих весов,
   время построения графа и время на один query после извлечения признаков.
   Оценить устойчивость к закрытию области номера на существующем аудите.

## Решение о включении в MVP

Ансамбль имеет смысл принять только при воспроизводимом приросте mAP@10 к
действующим **0,8147**, без существенного ухудшения F1/TNR и с учётом потери
баллов за скорость, если два encoder выйдут за пороги организаторов. Цель
эксперимента — не менее **+1 процентного пункта mAP@10**; меньший прирост
считать предварительным и разбирать по отдельным query и интервалу
неопределённости. Размер весов, офлайн-запуск и потоковая независимость —
обязательные условия независимо от прироста.

Если CLIP почти не добавляет правильных кандидатов и не исправляет порядок,
оставить один OSNet. Если помогает только в небольшом наборе случаев,
проверить, можно ли получить тот же эффект компактным парным реранкером
без постоянного запуска второго encoder. Эксперименты сохранять изолированно;
победитель не заменяет активную модель автоматически.
