# v23 — объединение MVP и выбранного v21

Открой `fuse_mvp_v21.ipynb` в прежнем исследовательском `.venv`: **Restart Kernel → Run All**. Настройки уже заполнены. Общего ограничения времени нет; сеть и GPU не нужны.

Используются только проверенные сохранённые признаки из завершённого `variant_22_final_comparison/runs/comparison_v1`. Изображения не проходят через encoder повторно. Нет нового обучения, пересчёта BatchNorm, дополнительных seed, внешних данных или замены MVP. Чтение исходных изображений для проверки checksum не является повторным извлечением признаков.

## Заранее фиксированная сетка

- MVP без изменений: λ=0.50, кандидат `ranking_top1`.
- Выбранный v21 без изменений: λ=0.65, кандидат `raw_top1`.
- Доля MVP 0.75, 0.50 или 0.25; для каждой λ=0.50 и 0.65. Во всех шести смесях кандидат `raw_top1`.

Всего **8 конфигураций на calibration**, включая два контроля. `k1=20`, `k2=3` не подбираются.

Смешивание выполняется в пространстве косинусной близости:

`z = L2(concat(sqrt(w) * MVP_512, sqrt(1-w) * V21_1536))`.

Координаты разных моделей не складываются. Смесь имеет 2048 измерений. Доля v21 внутри него распределена поровну между уже выбранными тремя encoder; эти веса и состав не меняются. Контроли возвращают исходные 512/1536-мерные массивы без лишнего преобразования.

## Выбор и проверка

1. Preflight проверяет завершённость v22, неизменность исходников/весов/данных, receipts и порядок строк кэша.
2. На исходной **calibration** для каждого варианта определяется свой порог по максимуму `C=0.7 F1+0.3 TNR` (при равенстве F1, затем больший порог).
3. Выбирается максимум **mAP@10 calibration**. При равенстве — C, затем порядок сетки (MVP, v21, смеси с большей долей MVP и λ0.50 прежде λ0.65). Контроль тоже может выиграть: принудительного выбора смеси нет.
4. Выбранная система, порог и два контроля сохраняются в `frozen_selection.json` **до загрузки массивов validation для расчёта**.
5. На validation оцениваются только выбранный вариант и два контроля. Если выиграл контроль, повторной копии той же оценки нет. Остальная сетка на validation не считается. После validation выбор не меняется автоматически.

MVP обучался на всех outer train ID, включая внутренние primary ID, поэтому его смеси нельзя честно выбирать по старым primary draws. Calibration и validation уже наблюдались в предыдущих экспериментах: это продолжение development-поиска, не новый независимый тест и не гарантированный результат на скрытом тесте.

## Выходные файлы

Новый каталог: `runs/fusion_v1/`.

- `manifest.json` — фиксированная сетка, источники и checksums.
- `frozen_selection.json` — выбор только по calibration, до validation.
- `results.json`, `REPORT.md` — вся calibration-сетка и validation только выбора/контролей; mAP, F1, TNR, C, отказы и попарные изменения.
- `tasks/evaluate_<система>/export/` — `submission.csv`, `candidates.csv`, реальные `embeddings.npy`, `embedding_order.json`.

`45×mAP+10×C` показывается справочно как два компонента оценки из 55 возможных баллов. Это не полный конкурсный балл и не замена объявленному критерию выбора по mAP.

Экспорты относятся к исходной validation, не к неизвестному test. Десять различных gallery-ID выводятся даже при отказе. При отказе строки в candidates.csv нет. Junk/top-10 оцениваются исходным evaluator без изменения разметки. Векторы идут в исходном порядке query, затем gallery. Описание выбранной смеси — исследовательская конфигурация, не готовый deployment bundle.

Контроли обязаны точно воспроизвести v22, включая пороги, метрики и per-query решения; допуски ради прохождения не расширяются. После сбоя повтори Run All с тем же именем: завершённые задачи восстанавливаются после проверки checksum. При изменении кода нужен новый `RUN_NAME`, а не перезапись истории.
