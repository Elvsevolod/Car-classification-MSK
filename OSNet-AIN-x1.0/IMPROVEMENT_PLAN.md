# План дальнейшего улучшения Vehicle ReID

Документ фиксирует идеи для следующих экспериментов после обучения
`variant_02_hpo_bnneck_supcon`. Это план, а не описание уже реализованных изменений.

## Текущая точка отсчёта

Лучшая модель: OSNet-AIN x1.0 с `P=16`, `K=2`, BNNeck, Supervised
Contrastive Loss, раздельными learning rate и staged Optuna HPO.

Метрики на текущем outer validation до приведения evaluator к уточнённому
организаторами протоколу:

| Метрика | Значение |
|---|---:|
| mAP | 0.810616 |
| Rank-1 | 0.801619 |
| Rank-5 | 0.902834 |
| mINP | 0.747183 |
| Candidate Precision | 0.581105 |
| Candidate Recall | 0.727679 |
| Candidate F1 | 0.646184 |
| TNR | 0.596774 |

Наблюдения:

- BNNeck и SupCon дали устойчивое улучшение относительно первого варианта;
- между seed остаётся заметный разброс;
- финальная модель достигла лучшего mAP примерно на пятой эпохе, после чего
  началось умеренное переобучение;
- дальнейший большой Optuna-поиск в том же пространстве, вероятно, даст меньше
  пользы, чем изменение pooling, backbone или схемы инференса.

## Приоритет 1: улучшения без нового обучения

### Flip TTA

Получать эмбеддинги исходного и горизонтально отражённого кропа, усреднять их и
повторно выполнять L2-нормализацию:

```text
embedding = normalize(embedding_original + embedding_flipped)
```

Нужно измерить прирост retrieval-метрик и удвоение времени инференса.

### K-reciprocal reranking

После косинусного поиска перестраивать список кандидатов по взаимным ближайшим
соседям. Матрицу расстояний внутри gallery можно вычислить заранее.

Проверить четыре режима:

1. текущий baseline;
2. только flip TTA;
3. только k-reciprocal reranking;
4. flip TTA и reranking вместе.

Параметры `k1`, `k2` и `lambda` подбирать только на calibration split. После
подбора заморозить их и один раз проверить на validation.

Отдельно проверить отказ от распознавания:

- порог по исходному cosine similarity;
- порог по reranking score;
- reranking только для порядка кандидатов, отказ по исходному cosine similarity.

Последний вариант предпочтителен как начальная точка: он меньше меняет смысл
уже откалиброванного confidence.

### Предобработка без искажения пропорций

Сейчас каждый BBox растягивается до `208x208`. Контролируемо сравнить:

- текущий square resize;
- aspect-preserving letterbox до `208x208`;
- прямоугольный вход, например `192x256` или `224x288`.

Нельзя заранее считать letterbox лучшим: исходная OSNet обучалась с квадратным
входом, поэтому результат нужно определить только по метрикам.

## Приоритет 2: OSNet variant 3

Следующий вариант должен сохранять победившие настройки variant 2 и менять по
одному компоненту за эксперимент.

### GeM pooling

Заменить Global Average Pooling на learnable GeM с начальным `p=3`. GeM меньше
сглаживает локальные отличительные детали автомобиля и регулярно применяется в
Vehicle ReID.

Первый эксперимент variant 3:

```text
OSNet-AIN + GeM + BNNeck + CE + SupCon
```

Остальные гиперпараметры оставить такими же, как у лучшей конфигурации variant 2.

### Early stopping и несколько seed

- добавить early stopping с patience 4–5 эпох по validation mAP;
- обучить минимум на seed `20260915`, `20260916`, `20260917`;
- сравнивать среднее значение и стандартное отклонение, а не лучший одиночный
  запуск;
- при необходимости усреднить нормализованные эмбеддинги двух лучших моделей.

Ансамбль нужно оценить с учётом удвоения размера и задержки инференса.

### MixStyle

Отдельной абляцией добавить MixStyle в ранние блоки encoder. Цель — снизить
зависимость от освещения, камеры и общего визуального домена, не передавая
метаданные камеры самой модели.

### Динамические веса функций потерь

Проверить расписание, при котором в начале сильнее влияет классификационная
голова, а затем возрастает вклад metric loss. Сравнить с постоянными весами из
variant 2.

### Circle Loss

Сравнить на одном протоколе:

- `CE + SupCon`;
- `CE + Circle`;
- комбинированный вариант только в том случае, если первые два показывают разные
  сильные стороны.

Не добавлять одновременно Triplet, SupCon и Circle без отдельной абляции.

## Приоритет 3: альтернативный backbone

Сравнить:

1. OSNet-AIN + GeM;
2. ResNet50-IBN + GeM + BNNeck;
3. TransReID с автомобильными предобученными весами.

Первым альтернативным backbone проверить ResNet50-IBN из FastReID: он проще для
локального обучения и ONNX-экспорта, чем Transformer. TransReID оставить
следующим экспериментом с потенциально более высоким потолком качества.

Выбирать модель по совокупности показателей:

- mAP, Rank-1, Rank-5 и mINP;
- Candidate F1 и TNR;
- разброс между seed;
- размер ONNX;
- задержка на CPU и MPS;
- совпадение результатов PyTorch и ONNX.

## Приоритет 4: внешнее автомобильное предобучение

Организаторы разрешили публичные и воспроизводимые внешние данные и веса. Этот
этап остаётся опциональным и запускается только после отдельного согласования
конкретного источника и проверки его собственных условий доступа:

```text
VeRi-776 / VehicleID / VERI-Wild
              ↓
автомобильное предобучение
              ↓
дообучение на локальном train
              ↓
калибровка порога отказа
```

Предпочтительно начать с готового официального vehicle checkpoint FastReID или
TransReID, а не с объединения нескольких сырых датасетов. Для источника нужно
зафиксировать URL, автора, точную версию/commit, лицензию и checksum. Разрешение
организаторов не отменяет собственные ограничения датасета на использование и
распространение.

Организаторский test нельзя использовать для обучения, подбора гиперпараметров
или порога отказа.

## Протокол честного сравнения

Поскольку outer validation уже использовался при разработке, есть риск
подстройки под него. Для новых архитектурных решений использовать
identity-disjoint cross-validation на 925 train identity, например три fold.

Рекомендуемый порядок:

1. разработка и подбор параметров на train folds;
2. калибровка порога на calibration split;
3. сравнение финальных кандидатов на outer validation;
4. выбор одной конфигурации перед финальным обучением;
5. test использовать только для формирования итоговых embeddings и candidates.

Для каждого эксперимента сохранять:

- точную конфигурацию и seed;
- checkpoint лучшего mAP, Candidate F1 и TNR;
- историю по эпохам;
- метрики среднего и разброса между seed;
- время обучения и инференса;
- версию preprocessing;
- параметры reranking и порог отказа.

## Что пока не делать

- не увеличивать число эпох без early stopping: текущий пик наступает рано;
- не запускать большой Optuna-поиск в неизменном пространстве параметров;
- не менять одновременно backbone, pooling, loss, resize и аугментации;
- не использовать DINOv2 zero-shot как финальный ReID encoder без дообучения;
- не использовать OCR, номер автомобиля, detector, tracking, время, географию
  или camera metadata во время инференса;
- не подбирать порог отказа на test.

`camera_id` допустим только как вспомогательная train/evaluation-информация,
например для формирования cross-camera positive. Он не должен входить в
эмбеддинг и не должен требоваться API при поиске.

## Этапы реализации

Каждый следующий этап начинается только после фиксации результатов предыдущего.
Это не позволяет одновременно поменять несколько компонентов и ошибочно приписать
прирост одному из них.

### Этап 1. Надёжный протокол оценки и экспорта

Статус: **выполнен 17 сентября 2026 года**.

- привести локальные mAP@10, Rank-1/5, mINP, F1 и TNR к опубликованным формулам;
- фильтровать как junk только пары с одновременным совпадением `vehicle_id` и
  `camera_id`, сохраняя негативы той же камеры;
- считать F1/TNR на уровне query по верхнему `confidence`;
- кодировать отказ отсутствием строк query в `candidates.csv`;
- валидировать формат `submission.csv`, `embeddings.npy` и `candidates.csv`;
- пересчитать baseline и зафиксировать новые числа.

Критерий завершения: синтетические тесты с вычисляемым вручную ответом проходят,
три экспортируемых файла проходят локальный валидатор. До появления официального
`evaluate.py` остаётся риск различий в неописанных пограничных случаях.

Зафиксированный результат текущего HPO checkpoint после исправления протокола:
validation mAP@10 `0.790162`, full mAP `0.803597`, Candidate F1 `0.725490`,
TNR `0.790323`, итог режима кандидатов `0.744940`. Порог cosine `0.595467` выбран
только на calibration.

### Этап 2. Улучшения инференса без обучения

Статус: **выполнен 17 сентября 2026 года**. Подробности и полный перебор:
[`stage_02_inference/`](stage_02_inference/).

- реализовать потокобезопасный k-reciprocal reranking: один текущий query и
  заранее рассчитанный граф gallery;
- сравнить baseline, flip TTA, reranking и их комбинацию;
- отдельно откалибровать отказ по raw cosine и reranking score;
- измерить latency `extract()` с TTA и время реранкинга.

Критерий завершения: выбран один режим по validation mAP@10 и баллу
`0.7 * F1 + 0.3 * TNR`, параметры заморожены на calibration.

Победитель: исходные OSNet-эмбеддинги + потоковый k-reciprocal reranking,
`k1=20`, `k2=3`, `lambda=0.5`; отказ остаётся по maximum raw cosine с порогом
`0.595467`. Validation mAP@10 вырос с `0.790162` до `0.814689`, Candidate F1 —
с `0.725490` до `0.728606`. Flip TTA не активирован: его p95 на локальном CPU
составил `40.80` мс, а итоговое качество с реранкингом оказалось ниже победителя.

### Этап 3. Предобработка и GeM

Статус: **выполнен 17 сентября 2026 года; GeM отклонён**.

- square resize и letterbox сравнены без обучения: `0.814689` против `0.667610`
  validation mAP@10 с активным реранкингом; сохранён square;
- создан `variant_03_gem` на настройках победителя variant 2;
- подготовлена парная абляция AvgPool/GeM на трёх seed с resumable early stopping;
- добавлены отдельные checkpoint, отчёты, ONNX-экспорт и parity-check.

AvgPool получил mean mAP@10 `0.800250 ± 0.005829`, GeM —
`0.791110 ± 0.007347`. GeM также ухудшил mean Candidate score:
`0.733111` против `0.757405`. Активный HPO checkpoint с mAP@10
`0.814689` остаётся в MVP.

Критерий завершения: улучшение подтверждено средним и разбросом по seed, а ONNX
совпадает с PyTorch и укладывается в ограничения скорости.

### Этап 4. Обучающая стратегия

Статус: **реализован 17 сентября 2026 года, ожидает полного запуска**.

- последовательно проверить MixStyle и более сложные негативы;
- сравнить постоянные и динамические веса loss;
- сравнить `CE + SupCon` и `CE + Circle`, не смешивая все metric loss сразу;
- повторить лучшие конфигурации на трёх seed.

Ноутбук: `variant_04_training_strategy/train_osnet_strategy.ipynb`.
Screening изолирован внутри 925 train identity; outer calibration/validation
не участвуют в выборе стратегии. Финальный отчёт отдельно сравнивает
победившую стратегию с matched-контролем и текущим MVP. Число финальных
эпох замораживается по best epoch победителя inner screening; outer validation
не используется для early stopping или выбора checkpoint.

Критерий завершения: остаётся только изменение, давшее воспроизводимый прирост
относительно победителя этапа 3.

### Этап 5. Альтернативные backbone

- первым проверить ResNet50-IBN + GeM + BNNeck;
- TransReID проверять только при недостаточном качестве более лёгких моделей;
- учитывать mAP@10, отказ, размер весов, latency и стабильность ONNX.

### Этап 6. Опциональное внешнее предобучение и финализация

- этап не запускается без отдельного согласования конкретного источника;
- предпочтителен публичный воспроизводимый vehicle checkpoint, а не смешение
  нескольких сырых датасетов;
- для источника фиксируются URL, автор, версия/commit, лицензия и checksum;
- после выбора конфигурации выполняются финальное обучение, экспорт, Docker и
  проверка всех артефактов одной командой.

Внешние данные разрешены организаторами, но не обязательны для этапов 1–5.
