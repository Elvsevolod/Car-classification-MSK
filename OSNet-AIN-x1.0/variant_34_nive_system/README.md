# v34 — конкретная NiVe-смесь в полной системе

Открыть `evaluate_nive_system.ipynb` с Python из проектной `.venv` и нажать **Run All**.
Это CPU-проверка уже обученных весов, а не очередное обучение. Лимита времени нет.
Основной результат: `runs/system_v1/REPORT.md` и `results.json`.

## Почему этот этап

В post-hoc анализе v33 равная смесь fold-matched R1 и N1/1800 (`aux_weight=0.025`)
дала inner mean mAP@10 **0.8481063717**, смесь с N0/1600 — **0.8462263071**.
Это не те же query/gallery, на которых v25 имеет **0.8289573904**: напрямую сравнивать
эти числа нельзя. Notebook проверяет найденные конкретные веса на исходных протоколах v25.

Автоматический single-model отбор v33 выбрал step0. Поэтому новый экспорт явно берёт
N1 **step1800**, N0 **step1600** и неизменный fold-matched parent **step0**. Checkpoints
закреплены SHA-256 в `configs/system_v1.json`; старые экспорты v33 не переписываются.

## Пять фиксированных вариантов

| Имя | Веса ranking | Граф k1/k2/λ |
|---|---|---|
| V25_control | .50 MVP + .50 full-train R1 equal3 | 20/3/.50 |
| R1_N0_pair | .50 parent + .50 N0/1600 | 20/3/.75 |
| R1_N1_pair | .50 parent + .50 N1/1800 | 20/3/.75 |
| MVP_R1_N0 | .50 MVP + .25 parent + .25 N0/1600 | 20/3/.50 |
| MVP_R1_N1 | .50 MVP + .25 parent + .25 N1/1800 | 20/3/.50 |

Смешиваются cosine-пространства через взвешенную конкатенацию нормированных векторов,
не усреднение координат разных моделей. Нового поиска весов/порогов/параметров графа нет.
Все пять вариантов заранее оцениваются на calibration и validation; calibration не выбирает
checkpoint или конфигурацию перед просмотром validation.

**Кандидат и отказ во всех случаях — прежний full-train R1 equal3**, raw top1 и порог
`0.534365177154541`. Его уверенность не приписывается первому изображению нового ranking.
CSV кандидатов обязан совпасть побайтно с v25. `raw` в per-query отчётах этого этапа означает
старый candidate-блок, не raw ranking новой пары.

## Что делает Run All

1. Компонентные тесты и проверка хешей исходных весов, данных, bbox, протоколов, старых отчётов и MVP.
2. Head-free ONNX-экспорт трёх выбранных checkpoints; фиксированный допуск `2e-5`.
3. Свежие ONNX-признаки на inner, сравнение с исходными признаками и **точными итоговыми graph top-10**.
   Raw пары — только диагностика: все его расхождения сохраняются явно, он не задаёт кандидата/отказ.
4. Небольшая свежая проверка исходного CPU-кэша и batch 1/8; затем полные новые признаки для двух исходных split.
5. Пять вариантов × два split, официальный evaluator, реальные three-file экспорты и replay из NPY.
6. Повторная проверка защищённых файлов и итоговая таблица mAP, Rank-1, F1, TNR.

Исключён только старый тест `test_notebook_has_clean_run_all_and_new_entrypoint`: он требует
пустых outputs у уже выполненного v33 notebook. Сохранённый пользовательский результат v33
ради этого не очищается. Проверки моделей, численных допусков и решений остаются включены.

Видны этап, модель, обработанные изображения, `fresh`/`cache` и время завершённых этапов.
Извлечение идёт batch 16, сохраняемые блоки — по 128 изображений. Это не эпохи обучения.
При повторном Run All сохранённые этапы проверяются по хешам и не выдаются за новый замер.
Повреждённый/несовместимый результат не подменяется новым молча. Конкурентные запуски
одного `RUN_NAME` запрещены. При ошибке нужно сначала разобраться с причиной, а не удалять проверки.

## Границы выводов и сохранность

- parent/N0/N1 обучены на 740 ID внутри original train; original calibration/validation с ними не пересекаются.
  В v25 — прежние full-train модели. Это честное сравнение готовых систем, но не равный объём обучения.
- N0/1600 и N1/1800 выбраны после inner-анализа, на разных шагах. Это контроль конкретных моделей,
  не новая причинная оценка пользы NiVe при одинаковом числе обновлений.
- Original validation уже многократно использована: результат — development evidence, не независимый test.
- Никакого обучения, BN-adaptation, threshold fitting, внешних загрузок, новых масок/OCR или изменения bbox.
- Старые runs/веса, активный v25 и приложение остаются неизменными. Автопродвижения, commit/push/merge нет.
- NiVe остаётся локальным. Для исследовательского preflight проверяется его прежнее происхождение;
  отдельный image-only runtime не читает NiVe, train, calibration и не требует PostgreSQL/сети.
- Для `MVP_R1_N1` сохраняется прежний candidate-ансамбль: 6 encoder forwards вместо 4 у v25.
  Это не заявление о скорости, Linux/GPU-приёмке или готовой конкурсной поставке.
- Устойчивость к сигналу номера не доказана. Ограничение junk/top-10 и официальный evaluator не меняются.

## Файлы и автономный прототип

`bundle.json` ссылается на новые ONNX и старый защищённый v24-профиль кандидатов;
это исследовательский bundle внутри checkout, не самостоятельный release-архив.
Все три новых ONNX сохраняются для сравнения; N0 не загружается при работе системы N1.

`V25_control` экспортирует исходный 2048D feature bank. Новые варианты — 3072D:
`MVP512 | candidate1536 | parent512 | selected_member512`, каждый блок настоящий float32.
Это **банк признаков с раздельными ролями**, не один cosine-вектор ранжирования.
NPY replay использует явные slices/веса из bundle; вспомогательная mINP по всему банку
не объявляется эквивалентной graph mAP@10. Полная поставка требует отдельного решения.

После notebook можно вызвать из корня репозитория:

```sh
ORT_DISABLE_TELEMETRY=1 .venv/bin/python -m training.nive_system_inference \
  --bundle OSNet-AIN-x1.0/variant_34_nive_system/runs/system_v1/bundle.json \
  --dataset /absolute/path/to/input \
  --output /absolute/path/to/new_output \
  --system MVP_R1_N1
```

Вход: `images/`, `test_query.csv`, `test_gallery.csv`; метки для инференса не нужны.
Выход: `submission.csv` (10 разных gallery ID даже при отказе), `candidates.csv`
(заголовок, принятые кандидаты), `embeddings.npy` (query, затем gallery), плюс описание порядка/ролей.
JPEG/PNG разрешаются однозначно; повреждённые веса, неправильный bbox, отсутствие или неоднозначность файла — ошибка.
Runtime — только явный CPU, без скрытого fallback. Точная сигнатура организаторского `extractor.py` не выдумывается.
