# v22 — сравнение сохранённых моделей

Открой `compare_saved_models.ipynb`, выбери прежний исследовательский `.venv` и нажми **Restart Kernel → Run All**. Интернет и другое устройство не нужны. Общего ограничения времени нет.

Цель — выбрать лучшую итоговую модель, а не самый стабильный рецепт обучения. Здесь нет нового обучения, изменения BatchNorm, подбора реранкера или усреднения результатов seed. Сравниваются конкретные системы:

| Система | Сохранённые веса | Реранкер | Кандидат |
|---|---|---|---|
| V21_selected_primary | avg seed15 (1400/1600/1700, BN уже сохранён в v20) + primary800 seed16/17 | 20 / 3 / λ0.65 | raw_top1 |
| R1_equal3_primary | primary800 seed15/16/17 | 20 / 3 / λ0.75 | raw_top1 |
| R1_equal3_full_v18 | готовый full-train ONNX equal3 из v18 | 20 / 3 / λ0.75 | raw_top1 |
| MVP_recalibrated | действующий ONNX MVP | 20 / 3 / λ0.50 | ranking_top1 |

Дополнительная строка `MVP_active` использует тот же свежий расчёт MVP и действующий порог `0.5948754549026489`. Рабочая конфигурация MVP не меняется.

## Порядок

1. Синтетические проверки и preflight: готовность v16/v18/v21, контрольные суммы источников, исходные протоколы и среда.
2. Свежие признаки на исходной calibration для всех четырёх систем. Для каждой — свой порог по максимуму `C = 0.7 F1 + 0.3 TNR`, при равенстве F1 и больший порог.
3. Фиксация всех систем и порогов в `frozen_comparison.json` **до** извлечения признаков validation.
4. Свежий расчёт на неизменённой исходной validation, проверка экспорта официальным evaluator и общий отчёт.

Primary-системы обучались на 740 ID, full-train и MVP — на 925. Мы сравниваем готовые веса, а не изолированный эффект рецепта. Outer ранее уже наблюдалась, в том числе при выборе MVP: этот расчёт — development-сравнение, не новая независимая оценка и не обещание результата на скрытом тесте.

## Результаты

Новый каталог: `runs/comparison_v1/`.

- `manifest.json`: фиксированные источники, составы, preprocessing из исходных моделей, протоколы и среда.
- `frozen_comparison.json`: пороги calibration и системы, зафиксированные до validation.
- `results.json` и `REPORT.md`: mAP@10, Rank-1/5, F1, TNR, C, принятые/отказы и попарные изменения.
- `tasks/evaluate_<система>/export/`: `submission.csv`, `candidates.csv`, `embeddings.npy`, `embedding_order.json`.

Это экспорты **validation**, не файлы сдачи для неизвестного test. Десять различных gallery-ID сохраняются и при отказе; отказ отсутствует в `candidates.csv`. Реальные float32-векторы идут в порядке исходного протокола: query, затем gallery. Junk/top-10 трактуются существующим официальным evaluator, без восстановления 11-го места и без изменения разметки.

Если выполнение прервано, повтори Run All с тем же `RUN_NAME`: завершённые задачи переиспользуются после проверки checksum. Изменённый код/состав требует нового имени, а не удаления истории. Время cached-задач не выдаётся за новый benchmark.

Torch-веса считают на исходном MPS; существующие ONNX — на явно выбранном CPU. Это сохраняет исходный вычислительный путь каждого артефакта, не является сравнением скорости устройств. Автоматического fallback и автоматической замены MVP нет. Исходные данные, bbox, веса, старые runs, приложение и релиз не изменяются.
