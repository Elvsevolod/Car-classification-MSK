# Этап 4 — скалярный реранкер на OOF-признаках

**Подготовлен, обучение ещё не запускалось.** Предыдущий этап: `variant_12_pair_reranker`. MVP, датасет, маски и исторические эксперименты не меняются. Новых зависимостей и скачиваний нет.

## Что запускать

Открыть **`train_oof_pair_reranker.ipynb`**, выбрать Python из `.venv` репозитория и выполнить **Run All**. Все этапы последовательные, ручного переключения флагов нет. По умолчанию CUDA → MPS → CPU; выбранное устройство печатается до обучения. На Mac с доступным Metal должно быть `mps`. Если напечатан `cpu`, а вы ожидали MPS, остановитесь до ячейки обучения и проверьте выбранное ядро.

Альтернатива из корня `Car-classification-MSK`:

```bash
.venv/bin/python -m training.oof_pair_reranker --device mps
```

Только проверка файлов, checksum, разбиений и доступного устройства — **без обучения и записи результатов**:

```bash
.venv/bin/python -m training.oof_pair_reranker --check-only
```

Путь результата: `results/run_01/`. После прерывания достаточно снова Run All: завершённые фолды пропускаются, незавершённый продолжается с последней **полностью сохранённой эпохи**. Эпоха, прерванная до checkpoint, повторяется. История восстанавливается из `last.pt`; удалять JSON не нужно. Два процесса на один run блокируются файловой блокировкой. Для изменённых данных, кода, устройства, библиотек или настроек нужен новый `OUTPUT` / `--output`, а не перезапись старого запуска. Готовый запуск проверяет SHA файлов и возвращает отчёт без повторных обучения и подбора.

Ноутбук должен оставаться запущенным, компьютер — включённым и без сна; закрытие крышки может приостановить вычисления. Эксперимент сам не меняет настройки питания. Точное время заранее неизвестно: после каждой эпохи выводятся её длительность, оставшиеся эпохи, ETA фолда и приблизительный ETA обучения всех encoder. Последний не включает извлечение признаков и отчёты. Предусмотрен запас минимум 1 GiB свободного диска; хранятся last/final, не все эпохи.

## Гипотеза

На предыдущем этапе обучающие пары головы происходили из encoder, который уже обучался на соответствующих автомобилях. На новых машинах пары могут быть сложнее. OOF (out-of-fold) означает, что **и query, и вся gallery каждого фолда извлекаются encoder, не обучавшимся на идентичностях и точных исходных кадрах этого фолда**.

Это проверка гипотезы, не обещание улучшения. Пилот variant 12 прибавил только 0,0574 п.п. mAP@10 к простому neighborhood-контролю. Новый отказ тогда ухудшил TNR, поэтому здесь механизм отказа не подбираем.

## Разделение и OSNet

1. Сохраняем outer train / calibration / validation: **925 / 307 / 309 identity**. Организаторские `test_query.csv`/`test_gallery.csv` не участвуют в обучении.
2. Внутри 925 identity создаём три фолда. Связанные identity, использующие один и тот же полный кадр по SHA-256, включая транзитивные связи, всегда остаются вместе. Разбиение воспроизводимо, seed `20260915`, баланс по числу identity.
3. Для каждого фолда новый `OSNet-AIN-x1.0` получает **stock-инициализацию**, не дообученные веса MVP. Градиенты считаются только по двум другим фолдам. Нельзя просто взять MVP и доучить на двух частях: он уже видел все 925 identity.
4. Рецепт берём из `variant_02_hpo_bnneck_supcon/results/selected_run_02/summary.json`, проверяя соответствие checksum активному ONNX. **Ровно 5 эпох**, как у активного checkpoint, с исходным **LR-горизонтом 30 эпох**. Это 5 первых эпох прежнего расписания, не новый cosine decay до нуля за 5 эпох. На меньшем train число batch/эпоху меньше; его записываем в отчёт. Все фолды используют один заранее выбранный seed.
5. Отложенные identity **не используются для early stopping, выбора checkpoint или настройки LR**. Нет промежуточной оценки на фолде: используется checkpoint последней, пятой эпохи. Модель при извлечении в `eval()`, статистики BatchNorm не обновляются.

Фиксированный рецепт: P=16, K=2 (batch=32), BNNeck, average pooling, square 208×208, SupCon + CE + consistency; encoder LR `0.00011940564013110387`, head LR ×10, weight decay `0.00006069870050850335`, SupCon weight `1.4948762510958067`, temperature `0.1`, consistency weight `0.22571745222502657`, label smoothing `0.1`, warmup 2 эпохи, min LR ratio `0.02`.

Используются прежние crop/аугментации: flip/color jitter, для robust-ветки blur/downscale/JPEG/random erasing/lower-center occlusion. Это **не** эксперимент с YOLO-масками. Исходные файлы не переписываются; OCR/камера/имя файла не являются входами модели. Камера используется только для cross-camera sampling/разметки пар/метрик.

## Пары, маленькая голова и контроль

Для каждой отложенной части строится отдельный `make_protocol(seed=20260915)`: один query на identity, около 20% open-set, cross-camera gallery. Реранкер получает raw cosine **top-50**, без искусственного добавления правильных ответов. Граф содержит только gallery, другие query не влияют на текущий запрос.

Объединяем **только 8 скалярных признаков**: cosine, 1−raw distance, 1−Jaccard, k-reciprocal similarity, neighbor support, mutual indicator, raw rank fraction, gap to best cosine. Координаты 512-D векторов разных OSNet не смешиваем. В основной inference остаётся один encoder MVP.

Положительные пары: одна identity, разные камеры; отрицательные: разные identity. Same-identity/same-camera junk и одинаковые исходные кадры игнорируются в loss, но не фильтруются по GT на inference. Каждый query имеет равный вес; позитивы/негативы балансируются внутри query. Стандартизация mean/std вычисляется только на валидных тренировочных парах.

Линейная голова 8→1, AdamW LR `0.01`, weight decay `0.001`, query batch=32, seed `20260915`, **7 фиксированных эпох**. Рецепт выбран предыдущим inner-пилотом и теперь не подбирается заново. Голова, обученная на OOF, **не переобучается затем на seen-признаках MVP** — иначе убрали бы смысл эксперимента. Обычного случайного train/val split pooled OOF-пар нет: он не обеспечил бы независимую оценку отбора головы, поскольку fold-encoder могли видеть identity другой части такого split.

Дополнительный дешёвый `matched_in_sample` контроль: **те же q/g каждого фолда, та же голова/seed/7 эпох**, но признаки извлекает MVP, обучавшийся на всех 925 identity. Он помогает отделить влияние OOF от изменения размера train-gallery по сравнению с variant 12. Это не идеальная причинная изоляция: отличаются также encoder и объём их обучения. Проверяем hit@50, позитивные пары и распределение признаков; эти диагностики не меняют бюджет обучения.

## Calibration и итоговая проверка

После обучения двух голов на неизменённых MVP-признаках outer calibration выбирается только beta из `0, 0.1, 0.25, 0.5, 1`. Формула: `(1−beta)*(1+neighborhood_score) + beta*sigmoid(head_logit)`. Критерий — mAP@10, затем Rank-1, затем меньшая beta. Sigmoid не объявляется калиброванной вероятностью.

Confidence остаётся **max raw cosine**, threshold — прежний из `artifacts/baseline_metrics.json`. Параметры фиксируются в `frozen_selection.json` до оценки validation. Сравниваем:

- `mvp`: исходный действующий поиск;
- `osnet_neighbors`: простой neighborhood-контроль этапа 1;
- `previous_head`: голова variant 12 с прежней beta, но **старым cosine-отказом**;
- `matched_in_sample`: новый контроль той же gallery на MVP-признаках;
- `oof`: новая OOF-голова на inference-признаках MVP.

У всех одинаковые outer query/gallery, эмбеддинги и правило отказа. Решения принять/отказать и TNR должны совпасть; F1 может меняться из-за правильности нового top-1. Считаются официальный mAP@10/Rank-1/5/F1/TNR, per-query различия, 2000 парных bootstrap-выборок (фиксированная gallery), CPU-поиск после эмбеддинга. `full_mAP`/`mINP` остаются диагностикой исходных векторов, не реранжированной выдачи.

Исправленный ручной masks-7 аудит также проводится без настройки порога. Он мал и уже использовался, поэтому не доказывает независимость от номеров. Outer validation тоже **не является новым независимым финальным тестом**: она использовалась в истории выбора MVP и других экспериментов.

## Выходные файлы

В `results/run_01/`:

- `experiment.json`: config, фолды, q/g, SHA данных/моделей/кода/исторических результатов, runtime;
- `folds/fold_01..03/`: `last.pt` (для resume), `final.pt`, `history.json`, `training.json`, `encoder.onnx`, `export.json`, диагностики;
- `cache/`: независимые OOF/MVP-кеши с fingerprint и записью после batch;
- `heads/oof/`, `heads/matched_in_sample/`: last/selected, история, head ONNX с проверкой PyTorch parity для batch 1/50/100;
- `fold_diagnostics.json`, `calibration.json`, `frozen_selection.json`;
- `RESULTS.md`, `report.json`: итоговые метрики, интервалы, масочный аудит и время;
- `validation/`: локальные submission/candidates каждой системы и неизменённые OSNet `embeddings.npy`, проверенные парсерами организаторов.

Никакого автоматического внедрения. Deployment потребует только **MVP ONNX + одну маленькую OOF-голову** (лимит 2 GB проверяется), а не три fold-encoder. Их веса нужны лишь для обучения/воспроизводимости. Текущий эксперимент не заменяет API, индекс или контейнер.
