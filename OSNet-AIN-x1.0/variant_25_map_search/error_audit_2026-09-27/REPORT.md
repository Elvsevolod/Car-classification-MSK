# Где v25 теряет mAP — 27 сентября 2026

## Вывод

**Рабочий v25 сохраняем. Следующий небольшой эксперимент — ограничить область перестановки
существующего реранкера, сохранив текущие веса и признаки. Новое обучение OSNet пока не первый шаг.**

Это вывод диагностики, а не уже полученное улучшение. Новые варианты поиска не оценивались.
Ни bbox, ни исходная validation, ни порог, ни MVP не изменены. Подозрительные примеры не исключались.

## Что проверено

Использованы сохранённые признаки MVP512 + R1_1536 из v22 и исходные протоколы,
защищённые manifest завершённого v29. Восстановлен действующий v25: fusion 50/50,
`k1=20`, `k2=3`, `lambda=0.5`, порог raw R1 `0.534365177154541`.
Метрики точно совпали с предыдущими результатами, validation top-10 — с экспортом v29.
Расчёт AP для каждого запроса независимо сверен с evaluator организаторов.
До и после анализа проверены SHA256 2934 файлов, включая входы, веса, исходники и результаты.
Нового encoder-инференса, обучения, калибровки и смены профиля не было.

59 тестов прошли, включая пять новых тестов диагностического расчёта.
Повторный запуск в новый временный каталог дал побайтно идентичный JSON:
SHA256 `3e57740b3946d0e849ff3ca55cceb0cafc0d20958c3747c88626c3a7e2d6a832`.
Код диагностики изолирован от inference и training; это применение `karpathy-guidelines`:
проверяемые расчёты без изменения рабочего алгоритма.

Оба split уже наблюдались. Анализ post-hoc и не является независимой оценкой скрытого теста.
Identity/camera используются только в evaluator и диагностике, не передаются поиску.

## 1. Реранкер полезен, но не во всех запросах

Здесь raw fusion — те же признаки 50/50, что у v25, но обычный cosine-порядок.
Это правильный контроль для измерения вклада реранкера, а не другой encoder.

| Система | Calibration mAP@10 | Validation mAP@10 | Validation Rank-1 | Validation Rank-5 |
|---|---:|---:|---:|---:|
| Только исходный MVP, raw | 0.756050 | 0.790162 | 0.789474 | 0.902834 |
| Только R1 equal3, raw | 0.813864 | 0.800363 | 0.805668 | 0.914980 |
| Fusion 50/50, raw | 0.800272 | 0.808091 | 0.821862 | 0.906883 |
| **Действующий v25** | **0.826410** | **0.828957** | **0.829960** | **0.878543** |

Реранкер даёт **+2.614 п.п. mAP на calibration и +2.087 п.п. на validation**.
На validation AP улучшается у 50 запросов, ухудшается у 22, неизменно у 175.
Rank-1 исправляется у 3 запросов и ломается у 1.
Просто отключать реранкер не следует: итоговый mAP станет ниже.

Но улучшение mAP не означает улучшение всех recall-показателей. Реранкер доводит до AP=1
181 запрос вместо 152 у raw fusion, одновременно ухудшая покрытие top-5/top-10.

## 2. Где уже находится хотя бы один верный ответ

Validation: 309 query / 896 gallery. В ranking-метриках 247 query с допустимым
cross-camera positive; остальные 62 учитываются в отказах, не получают AP=0.

| Пул первых K изображений | Raw fusion: query с позитивом | v25: query с позитивом |
|---|---:|---:|
| 10 | 234 / 247 | 229 / 247 |
| 20 | 239 / 247 | 237 / 247 |
| 50 | 242 / 247 | 240 / 247 |
| 100 | 243 / 247 | 242 / 247 |

При переходе raw → v25 **7 запросов теряют все позитивы из top-10, а 2 приобретают**.
В top-50 теряются 2 запроса, новых не появляется.
На calibration направление то же: в top-10 потеряны 7 и приобретён 1;
покрытие снижается с 235/246 до 229/246.

Объединение raw top-50 MVP и raw top-50 R1 содержит позитив всё для тех же 242/247
validation query. Это до 100 разных кандидатов, не равнозначно одному top-50.
Такое объединение само по себе пять самых тяжёлых запросов не решает.

## 3. Разложение текущей потери mAP

У v25 на validation:

| Состояние запроса | Число |
|---|---:|
| AP=1, ошибок по mAP@10 нет | 181 |
| Позитив есть в top-10, но AP<1 | 48 |
| Первый позитив на местах 11–20 | 8 |
| Первый позитив на местах 21–50 | 3 |
| Первый позитив на местах 51–100 | 2 |
| Первый позитив ниже 100-го | 5 |

30 запросов с наименьшим AP дают 66.9% суммарной потери относительно AP=1.
Это не основание обучаться на этих validation-примерах или исключать их.

Для каждого запроса рассчитан oracle: все **валидные** позитивы внутри данного пула
идеально переставлены наверх. Знаменатель AP — `min(всего валидных позитивов в gallery, 10)`;
одного найденного позитива недостаточно для AP=1 при нескольких обязательных позитивах.

Для фиксированного полного порядка v25 выполняется точное равенство:
`1 − AP = (oracle10 − AP) + (oracle50 − oracle10) + (1 − oracle50)`.

| Источник потери | Потеря mAP, п.п. | Доля всей потери |
|---|---:|---:|
| Неидеальный порядок внутри уже выбранных десяти | 6.245 | 36.5% |
| Недостающие в десятке позитивы, присутствующие в первых 50 | 7.512 | 43.9% |
| Недостающие позитивы за пределами первых 50 | 3.347 | 19.6% |

Oracle mAP@10 текущего пула v25: **0.891411 для K=10, 0.966532 для K=50**.
Для исходного raw fusion top-50: **0.966358**.
Это математические верхние границы с доступом к истинным меткам — **не прогноз достижимой
метрики и не реализуемая безошибочная модель**. Эти 80.4% потери внутри top-50 нельзя
называть гарантированно устранимыми: визуальной информации может быть недостаточно.

Файл сдачи остаётся ровно из десяти ID. Диагностика не подставляет 11-е изображение после
удаления junk. В текущих top-10 всех четырёх диагностических порядков junk не оказалось,
поэтому неоднозначность усечения здесь дала нулевую разницу; общее ограничение остаётся.

## 5. Следующий эксперимент — предложение, ещё не реализован

Предлагаю один короткий notebook на готовых признаках, **4 фиксированные системы**:

1. Действующий v25 без изменений — контроль.
2. `raw_pool10`: взять первые 10 raw fusion, упорядочить только их по существующей оценке v25.
3. `raw_pool20`: аналогично для первых 20.
4. `raw_pool50`: аналогично для первых 50.

За пределами пула сохраняется исходный raw-порядок. Речь о размере набора кандидатов,
а не о `k1`: параметры графа 20/3/0.5 и признаки fusion 50/50 остаются прежними.
Оценки графа вычисляются тем же кодом относительно статической gallery; они не переобучаются.
Кандидаты/уверенность/отказ по R1 не меняются. Нового encoder-инференса нет.

Гипотеза: сохранить полезную перестановку и ограничить вытеснение исходных кандидатов.
K=10 сохраняет **состав** raw top-10, но может потерять полезные новые позитивы, которые
обычный реранкер поднимает с более низких мест. Поэтому выигрыш не гарантирован.
K=20/50 проверяют менее жёсткое ограничение. Это не ещё одна сетка весов ансамбля или lambda
из v25/v26 и не повтор late fusion v27.

Выбор между тремя новыми вариантами — по calibration, при равенстве сохранить контроль;
на validation проверить контроль и один замороженный выбор. Не создавать новые варианты
после просмотра их validation. Протокол остаётся development, не независимым скрытым тестом.
Передача лучшей конкретной сборки в MVP требует реального сравнения, а не среднего по seed.

Если ограничение пула не даёт выигрыша, не расширять автоматически ещё одну сетку:
следующая отдельная гипотеза должна добавить информацию для различения трудных пар,
а не только переставлять те же глобальные оценки.

Почему не начать с уже знакомой local-head: v19 frozen 4×4 scorer не обошёл контроль;
v20 обучаемая 289→64→1 local pair-head также сохранила `baseline`. Это прежние внутренние
эксперименты, не прямое доказательство бесполезности всех парных моделей для v25,
но повторять их без существенного изменения гипотезы не стоит.

## 6. Правила и источники

Вопросы 9–10 `ORGANIZER_QA.md` явно допускают re-ranking top-K одного query относительно
статической gallery. Другие query, query expansion, test-метки и метаданные на входе поиска
не используются. Oracle по меткам допустим только в локальной диагностике.

Исходный k-reciprocal метод сочетает визуальную и Jaccard-дистанции:
[Zhong et al., CVPR 2017](https://openaccess.thecvf.com/content_cvpr_2017/html/Zhong_Re-Ranking_Person_Re-Identification_CVPR_2017_paper.html).
Ограничение raw-пула выше — наша проверяемая гипотеза по локальным данным,
не обещанный авторами статьи прирост и не перенос их transductive-реализации.

## Воспроизведение

Из корня research-репозитория, тем же `.venv`:

```sh
.venv/bin/python diagnostics/v25_error_audit.py --output /tmp/v25_error_audit_repeat.json
ORT_DISABLE_TELEMETRY=1 .venv/bin/python -m pytest -q tests/test_v25_error_audit.py
```

Выходной JSON должен быть новым: существующие файлы не перезаписываются.
`metrics.json` рядом с отчётом содержит все per-query числа, параметры протокола и checksums.
Скрипт не вызывает обучение, экспорт новых конкурсных решений и изменение приложения.
