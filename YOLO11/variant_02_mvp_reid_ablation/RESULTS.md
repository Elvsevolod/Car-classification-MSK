# Результат: автоматические маски на основной модели MVP

Дата: 2026-09-21. Источник чисел: `runs/paired_v1/comparison.json`.

**Вывод: добавление чёрных масок при неизменных весах текущего MVP ухудшило
качество поиска. В рабочий MVP маскирование не включено.** Это не означает,
что маски бесполезны при дообучении: такой эксперимент здесь не проводился.

## Что сравнивали

- Основная модель MVP: **OSNet-AIN x1.0 / HPO best-mAP epoch 5**, существующий
  `models/osnet_ain_x1_0_vehicle_reid_hpo_best_map.onnx`, ONNX Runtime CPU.
- Исходные кропы против тех же кропов после YOLO11n → непрозрачные чёрные маски.
  Обрабатывались и query, и gallery; исходные изображения не перезаписывались.
- Существующая outer validation из train.csv: **309 query / 896 gallery**,
  247 запросов с парой и 62 искусственных open-set запроса без пары.
- Одинаковые веса, порядок изображений, bilinear resize 208×208,
  ImageNet-нормализация, L2; без TTA и нового обучения.
- Реранкинг streaming k-reciprocal: k1=20, k2=3, lambda=0.5.
- Порог отказа **0.5948754549026489** по максимуму исходного cosine не менялся.
- YOLO: `variant_01_anonymized_regions/runs/pilot_01/weights/best.pt`.
  Маски взяты по замороженной validation-калибровке: confidence=0.20,
  margin=0.10 с каждой стороны. Сохранённые параметры инференса:
  imgsz=640, первичный conf=0.05, NMS IoU=0.45, затем фильтрация по 0.20.
  Расширение float-рамки выполняется до округления и обрезки границами кропа.
- Официальный evaluate.py через существующие адаптеры backend: mAP@10,
  same-ID/same-camera junk filtering, правила top-10 и отказов не менялись.
  Cross-query взаимодействия не добавлялись.

## Основной результат: с реранкингом MVP

Все значения в процентах; изменение — в процентных пунктах.

| Метрика | Без новых масок | С масками | Изменение |
|---|---:|---:|---:|
| mAP@10 | 81.47 | 77.66 | −3.81 |
| Rank-1 | 80.16 | 76.11 | −4.05 |
| Rank-5 | 88.26 | 85.43 | −2.83 |
| Candidate F1 | 72.86 | 71.29 | −1.57 |
| TNR: корректный отказ для запросов без пары | 79.03 | 79.03 | 0.00 |
| Candidate score: 0.7 × F1 + 0.3 × TNR | 74.71 | 73.61 | −1.10 |

- Правильный Top-1 среди 247 запросов с парой: **198 → 188**.
- Для 5 таких запросов Top-1 исправился, для 15 испортился.
- AP@10 вырос у 21 запроса, упал у 38, не изменился у 188.
- Из 62 запросов без пары система правильно отказала 49 в обеих версиях;
  ошибочно приняла 13 в обеих версиях. Это совпадение числа, а не обязательно
  одинаковый набор запросов.
- Отказы среди запросов с существующей парой: **73 → 78**.
- Решение «принять/отказать» изменилось у 17 запросов в общей выборке.
- По официальному подсчёту candidates: TP/FP/FN/TN **149/38/73/49 →
  144/38/78/49**. Эти категории следует трактовать по evaluate.py, а не как
  обычную бинарную confusion matrix всех 309 запросов.

Парный bootstrap по 247 запросам с парой, 2000 повторов, seed=20260921:
95% интервал изменения mAP@10 **[−6.07; −1.60] п.п.** Он не включает ноль.
Это локальная оценка при фиксированной gallery, не независимое подтверждение
качества на скрытом тесте организаторов.

## Что сделал детектор

- Обработано 1205 кропов; на 1202 применены маски, всего 1432 прямоугольника.
- Маски есть у 306 из 309 query и у всех 896 gallery.
- Средний cosine между исходным и замаскированным эмбеддингом: **0.9572**,
  медиана 0.9642, минимум 0.7049.
- Дополнительный подсчёт объединённой площади прямоугольников из кэша:
  в среднем закрыто **7.07% площади кропа**, медиана 6.68%, 95-й перцентиль
  11.46%, максимум 29.22%. У пяти кропов закрыто более 20%.
  Это общая площадь масок, **не доля ошибочно закрытой области**: полного
  ручного эталона для этих 1205 кропов нет.
- Для трёх кропов без найденных масок эмбеддинги обеих ветвей совпадают точно.

Извлечение обеих версий эмбеддингов с детекцией и сохранением кэша заняло
92.59 секунды на CPU. Это не отдельный latency benchmark и не измерение на
RTX A5000 организаторов.

## Что результат доказывает и чего не доказывает

1. При текущих весах и настройках добавлять автоматическое маскирование
   только на инференсе невыгодно по измеренным метрикам.
2. Хорошее покрытие анонимизированных областей детектором само по себе
   не гарантирует улучшения ReID.
3. Возможные причины падения: изменение внешнего вида входов, удаление
   полезных деталей около маски или использование моделью рисунка исходной
   анонимизации. Это **гипотезы**; данный опыт не разделяет их и не доказывает,
   что OSNet «читает номера».
4. Подбор другого порога отказа не исправит падение mAP@10: порог влияет
   на принятие кандидатов, но не восстанавливает их порядок.
5. OSNet checkpoint ранее выбирался по этой же outer validation. Результат
   полезен как парная диагностика, но это не новая независимая оценка модели.

## Следующий возможный эксперимент — пока не запущен

Сначала визуально проверить случаи ухудшения и самые большие маски. Затем
в изолированном варианте сравнить дообучение ReID с исходными изображениями,
автоматическими масками и их смесью при одинаковом бюджете. Настройки выбирать
по inner validation; параметры детектора оставить замороженными. Порог отказа
при необходимости калибровать отдельно, не по этому сравнению. Такой опыт
проверит, помогает ли адаптация к маскам; улучшение заранее не гарантировано.

Текущие веса, индекс и поведение MVP оставлены прежними. Новое обучение
и автоматическое переключение модели этим запуском не выполнялись.
